Azure Pipelines YAML Structure

1. Problem​

Teams moving from Classic (UI-based) pipelines to YAML often hit the same problems:

  • They don't know where the YAML file must live or how Azure DevOps finds it.
  • They mix up stages, jobs and steps, so builds and deployments run in the wrong order.
  • A file built in one job is "missing" in the next job, because each job on a Microsoft-hosted agent runs on a brand-new VM.
  • Deployments run when they shouldn't (for example, a feature branch deploying to production) because conditions are missing or wrong.

This page explains how a pipeline is structured, how files and values move through it, and the setup that is recommended for production.

2. Key terminology​

TermMeaning
PipelineThe whole YAML definition: triggers, variables, stages. One run = one execution.
StageA logical boundary (Build, Test, Deploy-Dev, Deploy-Prod). Stages run one after another by default.
JobA unit of work that runs on one agent. Jobs in a stage run in parallel by default.
Deployment jobA special job (deployment:) that targets an environment, records deployment history and supports approvals and strategies (runOnce, rolling, canary).
StepOne action in a job: a task, script, bash, pwsh, checkout, publish, download or template. Steps run sequentially.
TaskA packaged, reusable step, for example DotNetCoreCLI@2 or AzureWebApp@1.
AgentThe machine that runs a job: Microsoft-hosted or self-hosted.
Agent poolA group of agents. A job asks for a pool; any free agent in it picks up the job.
Pipeline artifactFiles published from one job and downloaded in later jobs/stages of the same run (or other pipelines).
EnvironmentA deployment target (dev, prod) with approvals, checks and history.

3. Where the YAML file lives​

Default location​

When you create a pipeline with the wizard (Pipelines → New pipeline → choose repo → Starter pipeline), Azure DevOps creates:

<repo-root>/azure-pipelines.yml
info

The default name is azure-pipelines.yml (plural "pipelines", no leading dot). It is only a convention. Any file name, any folder, and either .yml or .yaml works.

Custom location​

Point the pipeline to any path when you create it:

  1. Pipelines → New pipeline, then select the repository.
  2. Choose Existing Azure Pipelines YAML file.
  3. Select the branch and path, for example /.azure-pipelines/ci.yml.

For an existing pipeline: Edit → ⋮ (more actions) → Triggers → YAML tab → YAML file path.

With the Azure CLI:

create-pipeline.sh
# Requires the azure-devops CLI extension: az extension add --name azure-devops
az pipelines create \
  --name "app-ci-cd" \
  --repository "my-app" \
  --repository-type tfsgit \
  --branch main \
  --yml-path ".azure-pipelines/ci-cd.yml"   # custom path instead of the root default

Recommended repository layout (production)​

my-app/
├── src/
├── .azure-pipelines/
│   ├── ci-cd.yml                 # main pipeline (entry point)
│   ├── pr-validation.yml         # optional separate PR pipeline
│   └── templates/
│       ├── build-job.yml         # reusable job template
│       ├── deploy-stage.yml      # reusable stage template (dev/prod)
│       └── variables-common.yml  # shared variables
└── README.md
tip

Keep pipelines in a dedicated folder and move repeated logic into templates. One deploy-stage.yml template used for dev, test and prod ensures every environment is deployed the same way.

4. Pipeline structure: stages → jobs → steps​

The full hierarchy​

Pipeline (trigger, pr, variables, pool, resources, parameters)
└── stages
    ├── stage: Build
    │   └── jobs
    │       ├── job: Compile          ← runs on agent #1
    │       │   └── steps: checkout → script → publish
    │       └── job: UnitTest         ← runs on agent #2 (parallel by default)
    │           └── steps: ...
    └── stage: Deploy                 ← waits for Build by default
        └── jobs
            └── deployment: DeployWeb ← targets environment 'prod'
                └── strategy → runOnce → deploy → steps

Rules:

  • A pipeline has one or more stages. Stages run sequentially (each one depends on the one before it) unless you set dependsOn.
  • A stage has one or more jobs. Jobs run in parallel unless you set dependsOn, and only if you have enough parallel-job capacity.
  • A job has one or more steps, which always run sequentially on the same agent.

Implicit stage and implicit job​

You don't always have to write every level. Azure DevOps fills in the missing levels for you:

1-steps-only.yml
# Single stage + single job: write steps directly.
# Azure DevOps creates an implicit stage and an implicit job named "Job".
trigger: [main]
pool:
  vmImage: ubuntu-latest

steps:
  - script: echo "Hello from the implicit job"
    displayName: Say hello
2-jobs-only.yml
# Single stage, multiple jobs: write jobs directly (implicit stage).
trigger: [main]

jobs:
  - job: Build
    pool:
      vmImage: ubuntu-latest
    steps:
      - script: echo "build"

  - job: Lint
    pool:
      vmImage: ubuntu-latest
    steps:
      - script: echo "lint"   # runs in parallel with Build
3-full-stages.yml
# Multiple stages: full hierarchy.
trigger: [main]

stages:
  - stage: Build
    jobs:
      - job: Compile
        pool:
          vmImage: ubuntu-latest
        steps:
          - script: echo "compile"

  - stage: Deploy            # runs after Build (implicit dependsOn: Build)
    jobs:
      - job: Release
        pool:
          vmImage: ubuntu-latest
        steps:
          - script: echo "deploy"
You write at the top levelAzure DevOps createsUse when
steps:1 implicit stage + 1 implicit jobSimple CI: build/test in one place
jobs:1 implicit stageCI with parallel jobs (build, lint, tests on different OSes)
stages:Nothing implicitCI + CD, approvals, multiple environments (production)
warning

You can't mix these levels at the top. If you write stages:, you can't also write jobs: or steps: at the root of the file.

Types of steps​

step-types.yml
steps:
  - checkout: self                    # clone the repo (automatic in normal jobs)
  - script: npm ci                    # cmd on Windows, bash on Linux/macOS
  - bash: ./scripts/test.sh           # always bash
  - pwsh: ./scripts/check.ps1         # PowerShell Core, cross-platform
  - task: CopyFiles@2                 # a marketplace/built-in task
    inputs:
      SourceFolder: dist
      Contents: '**'
      TargetFolder: $(Build.ArtifactStagingDirectory)
  - publish: $(Build.ArtifactStagingDirectory)   # shortcut for PublishPipelineArtifact@1
    artifact: drop
  - download: current                 # shortcut for DownloadPipelineArtifact@2
    artifact: drop
  - template: templates/steps-lint.yml  # reuse steps from a template

Job types​

TypeSyntaxRuns onUse for
Agent job- job: NameAn agent (hosted or self-hosted)Build, test, scripts
Deployment job- deployment: Name + environment:An agentDeployments with history, approvals, strategies
Agentless (server) job- job: Name + pool: serverAzure DevOps server, no agentManual validation, delays, REST calls

5. Microsoft-hosted vs self-hosted agents​

How they behave​

Microsoft-hostedSelf-hosted
Who manages itMicrosoftYou (VM, VMSS, container, AKS)
Pool syntaxpool: { vmImage: ubuntu-latest }pool: { name: MyLinuxPool }
Machine per jobFresh VM for every job, destroyed afterwardsSame machine may be reused; workspace persists
Files from previous jobNever availableMight be there, but only if the same agent picks up the job, so don't rely on it
Private network accessNo (public internet only)Yes: can reach private endpoints, on-premises, VNet resources
Tools installedLarge preinstalled imageOnly what you install
Cost modelParallel jobs (free tier + paid)Parallel jobs + your infrastructure
Best forStandard builds, public endpointsPrivate networking, custom tools, large caches, compliance
pool-examples.yml
# Microsoft-hosted
pool:
  vmImage: ubuntu-latest

# Self-hosted pool with demands (pick an agent that has Docker on Linux)
pool:
  name: Prod-Linux-Agents
  demands:
    - agent.os -equals Linux
    - docker
danger

On a Microsoft-hosted agent, every job starts on an empty machine. If Job A builds dist/ and Job B needs it, Job B fails unless Job A publishes it and Job B downloads it. This applies inside the same stage too.

:::tip Self-hosted in production Use Azure Virtual Machine Scale Set agents or Managed DevOps Pools for elastic self-hosted agents, and clean the workspace (workspace: clean: all) so one run never sees another run's leftover files. :::

6. Passing files between jobs and stages​

CopyFiles is not a transfer between jobs​

CopyFiles@2 only copies files on the same agent, usually into $(Build.ArtifactStagingDirectory) to prepare a clean package. To move files to another job or stage, you need pipeline artifacts.

Job A (agent #1)                               Job B (agent #2)
build → CopyFiles → staging dir → publish ───► Azure DevOps ───► download → $(Pipeline.Workspace)/drop
                                               artifact storage

Option A: pipeline artifacts (recommended)​

Same stage, Job A → Job B​

same-stage-artifact.yml
jobs:
  - job: Build
    pool:
      vmImage: ubuntu-latest
    steps:
      - script: |
          mkdir -p dist
          echo "app v1" > dist/app.txt
        displayName: Build app

      - task: CopyFiles@2                       # stage only what you want to ship
        inputs:
          SourceFolder: dist
          Contents: '**'
          TargetFolder: $(Build.ArtifactStagingDirectory)

      - publish: $(Build.ArtifactStagingDirectory)
        artifact: drop                          # artifact name
        displayName: Publish artifact 'drop'

  - job: Test
    dependsOn: Build                            # REQUIRED: otherwise runs in parallel and the artifact isn't there yet
    pool:
      vmImage: ubuntu-latest
    steps:
      - download: current                       # 'current' = this pipeline run
        artifact: drop
      - script: cat $(Pipeline.Workspace)/drop/app.txt
        displayName: Use the file

Different stage, Build stage → Deploy stage​

cross-stage-artifact.yml
stages:
  - stage: Build
    jobs:
      - job: Build
        pool:
          vmImage: ubuntu-latest
        steps:
          - script: echo "app v1" > $(Build.ArtifactStagingDirectory)/app.txt
          - publish: $(Build.ArtifactStagingDirectory)
            artifact: drop

  - stage: Deploy
    dependsOn: Build
    jobs:
      # Normal job: you must download explicitly
      - job: Verify
        pool:
          vmImage: ubuntu-latest
        steps:
          - download: current
            artifact: drop
          - script: ls -R $(Pipeline.Workspace)/drop

      # Deployment job: artifacts of the current run are downloaded AUTOMATICALLY
      - deployment: DeployWeb
        environment: dev
        pool:
          vmImage: ubuntu-latest
        strategy:
          runOnce:
            deploy:
              steps:
                - script: ls -R $(Pipeline.Workspace)/drop   # already there
info
  • Artifacts belong to the run, so any later job or stage in the same run can download them.
  • The download location is $(Pipeline.Workspace)/<artifact-name>.
  • In a deployment job, add - download: none if you don't want the automatic download (it saves time).
  • PublishBuildArtifacts@1 / DownloadBuildArtifacts@0 (build artifacts) are the older approach. Prefer pipeline artifacts, which are faster and deduplicated.

Between different pipelines (CI pipeline → CD pipeline)​

cd-pipeline.yml
resources:
  pipelines:
    - pipeline: ci            # alias used below
      source: app-ci          # name of the CI pipeline in Azure DevOps
      trigger:
        branches: [main]      # run CD automatically when CI on main succeeds

steps:
  - download: ci              # download artifacts from the CI run that triggered this
    artifact: drop

Option B: external storage​

Push outputs to an external store and pull them later:

StoreGood for
Azure Container RegistryContainer images (build once, promote the same image through every environment)
Azure Artifacts feeds (Universal Packages, npm, NuGet, Maven)Versioned packages shared across pipelines and teams
Azure Storage (Blob)Very large files, or files that must outlive pipeline retention

Comparison​

Pipeline artifactsExternal storage
SetupNone, built inService connection, RBAC, storage
ScopeSame run / linked pipelinesAnything, any system
RetentionFollows the run's retention policyYou control it
SecurityAzure DevOps permissionsAzure RBAC / private endpoints
Best forBuild output → test → deployImages, shared packages, long-lived files

Production recommendation​

  • Application packages (zip, jar, static sites): pipeline artifacts. Build once in the Build stage and deploy the same artifact to dev → test → prod. Never rebuild per environment, so what you tested is exactly what you ship.
  • Container images: push to ACR in the Build stage, tagged with $(Build.BuildId) or the git SHA, and pass only the tag to later stages (see the next section).
  • Don't rely on shared folders on self-hosted agents. Jobs can land on different agents, and parallel runs overwrite each other.

7. Passing variables (values, not files) between jobs and stages​

For small values such as an image tag or a version, use output variables instead of artifacts.

output-variables.yml
stages:
  - stage: Build
    jobs:
      - job: Build
        pool:
          vmImage: ubuntu-latest
        steps:
          - bash: |
              TAG="1.0.$(Build.BuildId)"
              echo "##vso[task.setvariable variable=imageTag;isOutput=true]$TAG"
            name: setTag                      # step NAME is required to reference the output

      - job: Scan                             # same stage → use 'dependencies'
        dependsOn: Build
        variables:
          tag: $[ dependencies.Build.outputs['setTag.imageTag'] ]
        pool:
          vmImage: ubuntu-latest
        steps:
          - script: echo "Scanning image tag $(tag)"

  - stage: Deploy                             # different stage → use 'stageDependencies'
    dependsOn: Build
    jobs:
      - job: Deploy
        variables:
          tag: $[ stageDependencies.Build.Build.outputs['setTag.imageTag'] ]
        pool:
          vmImage: ubuntu-latest
        steps:
          - script: echo "Deploying image tag $(tag)"
From → ToExpression
Job → job, same stage$[ dependencies.<Job>.outputs['<step>.<var>'] ]
Job → job, different stage$[ stageDependencies.<Stage>.<Job>.outputs['<step>.<var>'] ]
Job → stage conditiondependencies.<Stage>.outputs['<Job>.<step>.<var>']
warning

If the value comes from a deployment job, the output path also includes the lifecycle/job name (for runOnce: <DeploymentJob>.<step>.<var> inside outputs[...]). Check the official "Set output variables" docs for the exact path for each strategy.

8. Conditions: controlling what runs​

By default, every stage, job and step has condition: succeeded(), which means it runs only if all its dependencies succeeded.

conditions.yml
stages:
  - stage: Build
    jobs:
      - job: Build
        pool:
          vmImage: ubuntu-latest
        steps:
          - script: echo build
          - script: echo "Collect logs even on failure"
            condition: always()                # runs whether earlier steps passed or failed

  - stage: DeployProd
    dependsOn: Build
    # Only deploy from main, and only if Build succeeded. Never from PRs.
    condition: |
      and(
        succeeded(),
        eq(variables['Build.SourceBranch'], 'refs/heads/main'),
        ne(variables['Build.Reason'], 'PullRequest')
      )
    jobs:
      - deployment: Prod
        environment: prod                      # approvals configured on the environment
        pool:
          vmImage: ubuntu-latest
        strategy:
          runOnce:
            deploy:
              steps:
                - script: echo deploy

  - stage: Notify
    dependsOn: DeployProd
    condition: failed()                        # runs only if DeployProd failed
    jobs:
      - job: Alert
        pool:
          vmImage: ubuntu-latest
        steps:
          - script: echo "Send alert to Teams/Slack/PagerDuty here"
FunctionRuns when
succeeded()All dependencies succeeded (default)
failed()Any dependency failed
succeededOrFailed()Dependencies finished, not cancelled
always()Always, even if cancelled
eq(), ne(), and(), or(), not(), contains(), startsWith()Combine with variables
danger

A custom condition replaces the default succeeded(). condition: eq(variables['Build.SourceBranch'], 'refs/heads/main') alone will deploy even if the build failed. Always wrap it: and(succeeded(), ...).

Three variable syntaxes​

SyntaxEvaluatedTypical use
${{ variables.x }} / ${{ if ... }}Compile time, before the run startsTemplates, parameters, including or skipping whole stages
$[ variables.x ]Runtime, before a job or stage startsConditions, output variables from other jobs
$(x)Runtime, just before each task runsInside scripts and task inputs

9. Production-recommended pipeline​

The complete pattern: build once → publish artifact → deploy the same artifact to dev → approve → prod.

trigger (main) ─► Stage: Build ─────────────► Stage: Dev ─────────► Stage: Prod
                  job Build                   deployment (env: dev)  deployment (env: prod)
                   ├ restore/build/test        auto-downloads 'drop'  approval check on env
                   ├ CopyFiles → staging       deploys                condition: main only
                   └ publish 'drop'                                   deploys same 'drop'
.azure-pipelines/ci-cd.yml
trigger:
  branches:
    include: [main]
pr:
  branches:
    include: [main]                 # GitHub/Bitbucket only (see note below)

variables:
  - name: vmImage
    value: ubuntu-latest

stages:
  # ---------- CI ----------
  - stage: Build
    displayName: Build & Test
    jobs:
      - job: Build
        pool:
          vmImage: $(vmImage)
        steps:
          - checkout: self
            fetchDepth: 1
          - script: |
              npm ci
              npm run build
              npm test
            displayName: Install, build, test
          - task: CopyFiles@2
            displayName: Stage deployable files
            inputs:
              SourceFolder: dist
              Contents: '**'
              TargetFolder: $(Build.ArtifactStagingDirectory)
          - publish: $(Build.ArtifactStagingDirectory)
            artifact: drop
            displayName: Publish artifact

  # ---------- CD: Dev ----------
  - stage: Dev
    dependsOn: Build
    condition: and(succeeded(), ne(variables['Build.Reason'], 'PullRequest'))
    jobs:
      - deployment: DeployDev
        environment: dev
        pool:
          vmImage: $(vmImage)
        strategy:
          runOnce:
            deploy:
              steps:
                # 'drop' is auto-downloaded to $(Pipeline.Workspace)/drop
                - task: AzureWebApp@1
                  inputs:
                    azureSubscription: sc-azure-dev      # service connection (workload identity federation)
                    appName: app-myapp-dev
                    package: $(Pipeline.Workspace)/drop

  # ---------- CD: Prod ----------
  - stage: Prod
    dependsOn: Dev
    condition: and(succeeded(), eq(variables['Build.SourceBranch'], 'refs/heads/main'))
    jobs:
      - deployment: DeployProd
        environment: prod                                # add Approvals & checks on this environment
        pool:
          vmImage: $(vmImage)
        strategy:
          runOnce:
            deploy:
              steps:
                - task: AzureWebApp@1
                  inputs:
                    azureSubscription: sc-azure-prod
                    appName: app-myapp-prod
                    package: $(Pipeline.Workspace)/drop

:::warning PR triggers in Azure Repos The pr: keyword works only for GitHub and Bitbucket Cloud repositories. For Azure Repos Git it is ignored. Configure PR validation with a branch policy instead: Repos → Branches → main → ⋮ → Branch policies → Build validation, and select this pipeline. :::

The three viewpoints​

ViewpointWhat this design gives you
ArchitectBuild once, promote many: the tested artifact is exactly what reaches prod. Separate service connections per environment limit how far a mistake can reach. Approvals live on the environment, not in YAML, so they can't be removed by editing the file.
Implementation engineerStages = environments, jobs = units of work, artifacts = hand-over between them. Templates remove repetition when more environments are added.
L2 / operationsEnvironment history shows which run and commit is deployed where. Rollback = re-run the Prod stage of the last good run. Failed stage logs show the exact step.

10. Best practices​

tip
  • Use stages: for anything that deploys. Keep steps:-only pipelines for simple CI.
  • Build once, publish once, and deploy the same artifact everywhere.
  • Always add dependsOn when a job needs another job's output.
  • Use deployment jobs + environments for deployments, which give you approvals, history and auto-download.
  • Use service connections with workload identity federation (no secrets to rotate).
  • Keep secrets in variable groups linked to Azure Key Vault, never in YAML.
  • Use templates for repeated stages and jobs, and pin template repos with ref:.
  • Wrap custom conditions in and(succeeded(), ...).
  • Pin images/versions you depend on (for example ubuntu-24.04 instead of ubuntu-latest) when reproducibility matters more than staying current.

12. Interview and client questions​

Q1. What's the difference between a stage, a job and a step? A stage is a logical phase (Build, Deploy) and stages run sequentially by default. A job runs on one agent, and jobs inside a stage run in parallel by default. A step is a single task or script, and steps run sequentially inside a job.

Q2. Can you write a pipeline without stages or jobs? Yes. With only steps:, Azure DevOps creates an implicit stage and job. With only jobs:, it creates an implicit stage.

Q3. How do you pass a build output from one stage to another? publish it as a pipeline artifact in the build job and download: current it in the later job. Deployment jobs download the current run's artifacts automatically.

Q4. Why is a file missing in the second job on a Microsoft-hosted agent? Every job gets a fresh VM that is discarded afterwards. Files must be passed through artifacts.

Q5. When would you choose self-hosted agents? When jobs need private network access (private endpoints, on-premises), custom or licensed tools, large persistent caches, or compliance control over the build machine.
